# 审查清单

配合 `SKILL.md` 使用。SKILL.md 规定顺序和门槛，本文件给出每个维度的检查项、红旗和取证要求。

## 使用方式

1. 按 SKILL.md 的维度顺序逐项过。
2. 每发现一个候选，先记在草稿里，不急着定级。
3. 全部过完后，回到 SKILL.md 的 CHECKPOINT 过滤候选。
4. 报出的每条都要能指到具体代码位置。

## 行为链路

沿输入到输出追一遍。链路断在哪，问题就在哪。

| 环节 | 要问的问题 |
| --- | --- |
| 入口与调用方 | 谁调用？同步还是异步？会不会重试？鉴权在哪一层？ |
| 参数与状态 | 谁校验？默认值是什么？空值、零值、负数、超长输入怎么处理？状态怎么迁移？ |
| 返回值与异常 | 异常向上传播还是被吞？错误码和文案一致吗？调用方判空了吗？ |
| 数据格式 | 编码、单位、时区、精度、排序、schema 版本是否一致？ |
| 权限 | 谁能调用？租户或用户隔离在哪做？会不会越权？ |
| 生命周期 | 创建、更新、删除、级联、孤儿数据、软删除怎么处理？ |
| 事务与并发 | 原子性够吗？隔离级别是什么？锁顺序固定吗？重入或重复提交会怎样？ |
| 幂等与守卫 | 查重/幂等键由哪些字段组成？守卫集合收录的是「在借」还是「全部」、批内还是库内？跨集合放行是否把不该放的行放过去了？ |
| 测试与配置 | 既有测试和配置有什么约定？新代码遵守了吗？环境差异会不会改变行为？ |

## 典型错误类别

按类别扫一遍，避免只盯自己熟悉的类型。

| 类别 | 常见表现 |
| --- | --- |
| 结构 | 放错层、循环依赖、模块职责漂移、接口暴露过多 |
| 数据 | 类型不匹配、边界值、未初始化、精度丢失、编码错误、空值传播 |
| 实现与意图不符 | 注释与代码不一致、变量名误导、分支写反、漏掉需求分支 |
| 构造 | 依赖注入缺失、初始化顺序错误、资源未释放、配置默认值错误 |
| 集成 | 接口契约不符、错误码映射错误、重试与幂等缺失、版本不兼容 |
| 需求理解 | 实现满足字面要求但违背真实意图、漏掉例外场景 |
| 测试定义 | 测试断言错误、测了 mock 没测行为、测试与实现一起错 |

## Design

| 检查项 | 红旗 | 取证要求 |
| --- | --- | --- |
| 模块边界 | 一个模块同时负责解析、校验、持久化和展示 | 指出职责混在一起的具体函数或文件 |
| 依赖方向 | 底层模块反向依赖上层；业务代码依赖 UI 框架细节 | 给出 import 或调用位置 |
| 放置位置 | 通用能力写进业务模块；只服务一个调用方的代码进了公共库 | 说明哪些调用方需要它 |
| 集成方式 | 新功能绕过既有入口，另开一条并行路径 | 指出两条路径及分叉点 |
| 实施时机 | 为未确定的需求提前抽象；为一次性场景引入框架 | 说明当前真实需求是什么 |
| 模块深度 | 接口参数和配置项接近功能本身；调用方要懂内部细节 | 列出接口签名和调用方需要知道的内部知识 |
| 信息隐藏 | 同一份格式或协议知识散落多处 | 给出两处以上位置 |
| 语义归属 | 行为的状态、变更权、生命周期、不变量和失败策略没有唯一所有者 | 列出所有写入点，指出谁是所有者 |
| 真源分散 | 同一事实（配置、常量、schema、权限表）在两处定义 | 给出两处定义和同步方式 |
| 范围蔓延 | 改动顺带做无关重构、重命名或功能扩展 | 指出与本次意图无关的改动 |

## Functionality

| 检查项 | 红旗 | 取证要求 |
| --- | --- | --- |
| 意图一致 | 代码实现与 PR 描述、提交信息、注释说的不是一件事 | 引用原文与代码位置 |
| 边界值 | 空、零、负数、最大值、超长、重复值未处理 | 给出触发输入 |
| 空值与缺省 | 调用方可能传空；默认值掩盖了配置缺失 | 指出调用方与默认值来源 |
| 并发 | 共享状态无锁；锁顺序不一致；检查与使用之间存在竞态 | 画出两个并发路径 |
| 状态迁移 | 非法状态组合可达；状态回退缺失 | 列出状态表与实际迁移 |
| 错误路径 | 异常被吞；部分失败后数据停在中间态 | 指出 catch 或事务边界 |
| 用户可见行为 | 提示文案、排序、分页、导出结果与预期不符 | 给出复现步骤或输入 |
| 布局常量 | 固定偏移、列宽、高度假设了内容行数或视口不变 | 内容增行、视口收窄、选项数量变化后是否溢出或遮挡 |

## Complexity

| 症状 | 检查问题 | 红旗 |
| --- | --- | --- |
| 变更放大 | 改一个概念要动几处？ | 同一规则在多个文件重复出现 |
| 认知负担 | 用这个模块要先知道多少别的东西？ | 调用方需要了解内部缓存、锁、重试细节 |
| 未知的未知 | 改这里会不会影响别处？看得出吗？ | 隐式全局状态、事件顺序依赖、魔法配置 |

只解决现在已知的问题。为猜测中的未来需求增加抽象层、配置项或扩展点，记 P3，并说明当前真实需求。

## Errors / Contracts

| 检查项 | 红旗 | 取证要求 |
| --- | --- | --- |
| 语义重定义 | 能用「不存在」「空结果」表达的情况，被做成异常分支 | 给出可替代的语义 |
| 异常面 | 新增异常类型或错误码，调用方必须逐个处理 | 列出接口抛出的全部异常 |
| 错误处理自身 | catch 里再抛新异常；错误包装丢失原因；重试逻辑放大故障 | 指出 catch 或重试代码 |
| 部分失败 | 多步写入无事务；失败后留下半成品 | 指出步骤与失败点 |
| 幂等 | 重试或重复提交会重复写入 | 给出重复调用路径 |
| 契约一致性 | 文档、类型、运行时校验三处不一致 | 列出三处定义 |
| 多阶段写入 | 声明「任一失败则零写入」的流程跨几次写入；逐阶段列出失败点与重传结果 | 指出每个写阶段与失败后的重传路径；项目 ADR 否决长事务不等于允许非原子 |
| 安全阀位置 | 上限、限额或预算的判定放在同一批数据的无界读取之后：超限请求在返回错误前已把全量数据读进内存，安全阀只省下后续生成时间，锁不住峰值 | 按执行顺序列出「哪次查询无界、判定在第几步」；判定必须早于无界查询 |

### 安全快速检查

只查可利用的问题，不把理论风险写成阻断项。完整安全审计交给 security-review。

| 检查点 | 红旗 | 取证要求 |
| --- | --- | --- |
| 注入 | SQL、命令、模板、路径拼接未过滤输入 | 从输入追到执行点 |
| 认证授权 | 接口漏鉴权；只检查登录中间件，不检查对象级权限和租户隔离 | 指出路由和资源归属判断 |
| 密钥 | 硬编码 token、密码、私钥；日志打印敏感信息 | 指出位置，报告时脱敏 |
| 路径穿越 | 外部文件名直接拼路径，未拦 `..` | 指出输入和文件操作点 |
| 反序列化 | `eval`、`pickle`、不安全 YAML、类型范围过宽的反序列化 | 指出输入来源和解析器 |
| 依赖 | 已知漏洞版本；未核对 lockfile | 给出依赖名、版本和审计依据 |
| Web 攻击 | 未转义输出、缺 CSRF 防护、CORS 过宽 | 指出输出点和安全配置 |

## Tests

先按本表过一遍，再按 `references/test-quality.md` 的 T1-T6 查测试腐化。

| 检查项 | 红旗 | 取证要求 |
| --- | --- | --- |
| 失败能力 | 实现改坏时测试仍通过；用例入参不等于真实运行状态（真实为 true 却传 false），删掉被保护的分支仍绿 | 指出断言覆盖不到的分支；用「删掉目标分支，用例必须红」自检 |
| 安全阀断言 | 上限用例只 mock 超量数据、不断言查询参数，删掉 `take` 或写成 `limit`（少 1）仍绿；缺「恰好 limit 条放行」边界 | 断言查询参数含 `take: LIMIT + 1`，并补边界放行用例 |
| 假阳性 | 断言只检查 mock 被调用；断言与实现同错 | 引用断言代码 |
| 断言质量 | 只断言非空、只断言状态码、不断言关键字段 | 指出缺失的断言 |
| 覆盖新增分支 | 新条件、新错误路径、新边界无对应用例 | 列出未覆盖分支 |
| 测试隔离 | 用例依赖执行顺序、共享可变状态、依赖真实时钟 | 指出耦合点 |
| 测试层级 | 业务规则只在小单测里验证；集成契约无端到端覆盖 | 说明改动类型与应有层级 |
| 测试腐化 | 测试意图不清、脆弱、重复、mock 滥用、覆盖率幻觉、层级错配 | 指出具体测试或缺失用例 |

测试无法运行时，静态审查测试代码，并标注「测试行为未实测」。

## Naming

| 检查项 | 红旗 |
| --- | --- |
| 语义准确 | 名字说 A，实际做 B；`data`、`info`、`temp`、`handle` 这类空名 |
| 作用域匹配 | 全局变量用短名；局部变量用超长名 |
| 问题域命名 | 按实现细节命名（`MapWrapper`），不按业务概念命名（`BorrowPolicy`） |
| 一致性 | 同一概念出现多个叫法，或同一叫法指多个概念 |
| 误导性 | `isXxx` 返回非布尔；`getXxx` 有副作用 |

## Comments

| 检查项 | 红旗 |
| --- | --- |
| 解释原因 | 注释复述代码做什么，不解释为什么这么做 |
| 失效注释 | 注释与代码不一致；旧 TODO 已无意义 |
| 反直觉技术 | 用了不直观的做法，却没写直白做法和收益 |
| 复杂逻辑 | 正则、位运算、算法没有解释性注释 |
| 用注释补代码 | 代码本身难懂，靠注释解释；应先简化代码 |

## Style / Consistency

| 检查项 | 红旗 |
| --- | --- |
| style guide | 违反项目明文规范 |
| 现有风格 | 同文件内命名、结构、错误处理风格不一致 |
| 改动边界 | 功能改动夹带大范围格式化或重命名 |
| 个人偏好 | 只是作者或审查者更喜欢另一种写法 |

纯个人偏好不阻塞提交。重大风格改动要求独立成一个改动。

## Documentation

| 检查项 | 红旗 |
| --- | --- |
| 构建与运行 | 新增依赖、环境变量、启动步骤未写文档 |
| 测试方式 | 新测试的运行方法未说明 |
| 交互与契约 | API、CLI、配置格式变化未更新文档 |
| 发布说明 | 用户可见变化未进 CHANGELOG 或发布说明 |
| 地图漂移 | 项目文档或架构地图与代码不一致；改动后未更新 |
| 删除同步 | 删了代码或功能，文档仍保留 |
| 声称的兜底 | 文档或计划声称的兜底、重试、联动，在代码里找不到调用点——按「文档与代码不符」报出 |
| 机制描述 | 注释或计划声称的刷新、重试、聚焦行为，被全局默认配置反向覆盖（如全局关 `refetchOnWindowFocus`，而 hook 注释称窗口聚焦会重取）；顺注释查全局默认项与调用链 |

## 验证命令参考

只运行项目已经声明的命令。不要为了跑检查而自动安装依赖、联网或执行破坏性迁移。命令不存在或环境不支持时，记录原因。

| 生态 | 最小检查 |
| --- | --- |
| JavaScript / TypeScript | 项目 scripts 里的 lint、`tsc --noEmit`、单元测试、构建 |
| Python | `ruff` 或 `flake8`、`mypy` 或 `pyright`、`pytest` |
| JVM | 仓库 wrapper 的 `mvn test` / `verify` 或 `gradle test` / `check` |
| Go | `go test ./...`、`go vet ./...`，必要时加 `-race` |
| Rust | `cargo test`、`cargo check`、`cargo clippy` |
| C / C++ | 项目构建、`clang-tidy`，必要时加 sanitizer |
| .NET | `dotnet test`、`dotnet build` |
| 通用 | 类型检查、相关单测、构建；只跑与改动相关的最小集合 |

## 误报控制

报出每条候选前，逐项确认：

1. 代码路径真的可达吗？
2. 影响是理论，还是有可复现的触发条件？
3. 规则适用于当前语言、框架和版本吗？
4. 项目配置是否明确允许这种写法？
5. 是否来自生成代码、测试夹具或框架约定？
6. 无法确认时，是否降为「待确认事项」，而不是 P0/P1？

只有证据充分才阻断。不要把「看起来不常见」当成证据。
