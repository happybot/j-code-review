# 结构与抽象红旗

配合 `SKILL.md` 的「结构与抽象红旗」一节使用。这里给出每类红旗的判定信号、为什么增加复杂度、以及改法方向。

## 总原则

复杂度由依赖和模糊累积而成。审查不只把代码收拾干净，还要找机会删除复杂度。对小恶化零容忍。

每条红旗都要落到具体位置。指不出位置，就还没有证据。

## 浅模块 / 薄 wrapper

**判定信号**：

- 接口参数、配置项、调用步骤的总量和功能本身差不多。
- 方法只做转发：签名与下层相同，方法体只有一行调用。
- wrapper 没有增加校验、缓存、重试、适配、日志或语义收敛。

**为什么增加复杂度**：调用方多经过一层间接，却得不到更简单的接口。层数增加，理解成本增加，收益为零。

**改法方向**：删掉 wrapper，直接调用下层；或让 wrapper 真正变深，把多个底层调用收敛成一个简单接口。

## 信息泄漏

**判定信号**：

- 同一份知识出现在多个模块：文件格式、协议字段、魔法字符串前缀、状态编码、排序规则。
- 修改一处格式，要同步改多处。
- 按执行顺序拆模块（时间顺序分解），解析、校验、转换各占一个模块，每个模块都知道同一份格式。

**为什么增加复杂度**：知识重复意味着改动会放大，且容易出现不一致。后门泄漏不经过接口，更难发现。

**改法方向**：把知识收进一个模块，只暴露必要接口；或把按时间拆开的步骤合并到同一个信息所有者下。

## 真源分散 / 语义归属不清

**判定信号**：

- 同一状态有两个以上写入者，谁都能改。
- 同一事实（配置、常量、schema、权限表、状态编码）在两处定义，需要手工同步。
- 行为的状态、变更权、生命周期、不变量和失败策略分散在多个模块。
- 改动让一个概念跨了两个所有者，或者让只读副本变成了可写副本。

**为什么增加复杂度**：变更放大，责任不清，两个所有者会逐渐漂移。读者无法判断哪个来源是权威。

**改法方向**：指定唯一所有者。把状态、变更权、生命周期、不变量和失败策略收在一处。只读副本可以保留，写入必须经过所有者；确实需要同步时，用生成或单向投影，不手工双写。

## 面条式特例增长

**判定信号**：

- 已有路径上不断叠加 `if (specialCase)`、`flag`、一次性开关。
- 新增需求通过再加一个分支解决，状态组合越来越多。
- 同一函数里出现多个互斥条件，组合关系说不清。

**为什么增加复杂度**：分支组合爆炸，读者要同时理解所有特例。小复杂度持续累积，最终无法局部修改。

**改法方向**：建立显式状态模型，或抽出专用策略；把特例收敛成数据或状态迁移，不继续加条件。

## 重复

**判定信号**：

- 同一段代码或同一业务规则在多处出现。
- 修一个 bug 要改多个副本。

**为什么增加复杂度**：重复说明还没找到正确的抽象。两处副本会逐渐漂移。

**合并前先确认**：两块代码是否共享信息、是否一起使用、概念是否重叠。只是长得像但变化原因不同，分开更好。错误合并会把两个独立概念绑死。

**改法方向**：共享信息且一起变化的，合并成一处；只是形似的，保留分开，并说明理由。

## 连体方法

**判定信号**：

- 拆开后，读其中一个必须来回参照另一个。
- 两个方法的参数和状态高度重叠。
- 拆分的唯一理由是行数。

**为什么增加复杂度**：读者要在两个位置之间跳转，接口数量增加，理解成本上升。深度优先于长度：几百行但接口简单的方法，可以是好模块。

**改法方向**：合并回一个方法，或按真正的概念边界重新拆；不以行数作为拆分依据。

## 透传变量

**判定信号**：

- 中间层的参数只为把值从上层传到下层。
- 中间层不使用这个参数，也不校验或转换它。
- 每新增一个底层参数，整条调用链都要改签名。

**为什么增加复杂度**：调用链上的每一层都被迫知道与自己无关的数据。

**改法方向**：改用 context 对象、请求作用域对象或共享状态；让中间层只依赖自己真正需要的东西。

## 类属炎（classitis）

**判定信号**：

- 为拆而拆出一堆小类、小方法和接口。
- 系统里的接口总数远多于实际概念数。
- 每个类只做一件很小的事，组合起来要读很多文件。

**为什么增加复杂度**：局部简单，系统级复杂。读者要维护大量跨文件关系。

**改法方向**：按概念聚合，不按行数机械拆分；删除没有独立变化原因的类。

## 文件越过 1000 行红线

**判定信号**：

- 单个文件超过 1000 行。
- 文件内出现多个互不相关的职责。
- 改动经常集中在文件的不同区域，且区域之间没有共享状态。

**为什么增加复杂度**：导航成本高，冲突概率大，职责边界模糊。

**改法方向**：按职责拆分，优先沿真实边界拆；有强结构理由时可以保留，但要在审查中说明理由。

## 死代码与残留

**判定信号**：

- 删除功能后，类型联合、常量、配置项、样式、token 仍有残留。
- grep 只命中定义，没有消费者。
- 兼容分支对应的旧版本已经不再支持。

**为什么增加复杂度**：读者无法判断哪些代码还有效，后续改动容易踩到死路径。

**改法方向**：确认无消费者后删除；确实要保留的，写明保留原因和删除条件。

## 「也许改个名」不算简化

**判定信号**：

- 建议只停留在改名、换行、调整顺序。
- 已经有明显更简单的思路，改动只是把原思路稍作收拾。

**为什么不算**：这类建议不改变结构，不减少复杂度。

**改法方向**：指出更简单的结构方案；没有方案时，不把改名当审查成果。

## 偏好直接、无聊、可维护的代码

**判定信号**：

- 引入聪明但难懂的技巧，收益不足以抵消理解成本。
- 为少量代码引入复杂框架或元编程。
- 抽象层数超过实际变化点。

**改法方向**：优先直接写法；把聪明技巧限制在局部，并用注释写明直白做法和收益。
