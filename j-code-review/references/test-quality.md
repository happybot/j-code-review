# 测试质量

按六类测试腐化风险检查。每条都问：测试坏掉时，它会不会真的失败？只在能指出具体测试或缺失用例时报告。

## T1 测试意图不清

| 检查问题 | 红旗 | 不要误报 |
| --- | --- | --- |
| 读这个测试，能知道它在验证什么吗？ | 测试名是 `test1`、`shouldWork`；断言没有说明；测试依赖外部 fixture，正文看不出前提 | 多个断言围绕同一行为，能讲清一个故事时，不算问题 |
| 测试正文是否必须读生产代码才能理解？ | 测试里有大段 setup，关键输入藏在共享 fixture | 共享 setup 对每个用例都相关时，可以接受 |

## T2 测试脆弱

| 检查问题 | 红旗 | 不要误报 |
| --- | --- | --- |
| 行为不变的重构会不会让测试失败？ | 断言私有方法、内部状态、实现细节；断言 mock 调用顺序或无关参数 | 验证外部可观察事件或发出的命令，不算实现耦合 |
| 测试是否依赖时间、随机数、执行顺序或共享状态？ | 同一测试多次运行结果不同；用例之间互相影响 | 测试显式注入固定时钟或随机种子时，不算脆弱 |

## T3 测试重复

| 检查问题 | 红旗 | 不要误报 |
| --- | --- | --- |
| 同一场景是否在多个测试里重复验证？ | 多个测试验证完全相同的行为；同一场景在单元、集成、端到端三层重复，且没有不同风险 | 同一场景在不同层验证不同风险时，不算重复 |
| 测试 helper 和 fixture 是否重复复制？ | 多份几乎相同的 setup 或断言，改一处要改多处 | 少量局部重复比过度抽象更清楚时，可以接受 |

## T4 Mock 滥用

| 检查问题 | 红旗 | 不要误报 |
| --- | --- | --- |
| 测试是否比被验证的行为更复杂？ | mock 设置代码超过测试主体；单个测试超过 3 个 mock | 少量 mock 隔离不确定依赖，断言仍验证行为时，可以接受 |
| 主断言是否只验证 mock 被调用？ | `expect(mock).toHaveBeenCalledWith(...)` 是唯一断言；生产代码坏了也能通过 | 交互本身就是被测行为时，一次调用断言是合理的 |
| 是否为测试在生产类里加方法？ | 生产类出现只有测试调用的生命周期方法 | 测试用 fake 或 spy 观察状态迁移，不算 |

## T5 覆盖率幻觉

| 检查问题 | 红旗 | 不要误报 |
| --- | --- | --- |
| 覆盖率是否掩盖了未验证的失败路径？ | 行覆盖率高，但错误分支、边界、异常路径没有用例 | 覆盖率配合分支、边界和变更路径覆盖时，是有用信号 |
| 是否只测 happy path？ | 没有空值、空集合、零值、并发或失败用例 | 新模块早期覆盖率低但风险低时，可以先记录缺口 |
| 是否只断言返回值，不断言关键副作用？ | 数据库写入、事件发布、状态迁移没有断言 | 副作用在集成测试里断言时，不算缺口 |

## T6 测试结构错配

| 检查问题 | 红旗 | 不要误报 |
| --- | --- | --- |
| 测试层级是否匹配风险？ | 端到端和集成测试数量超过单元测试；高风险路径和低风险路径密度相同 | 平台约束或产品风险可以解释比例偏差 |
| 修改遗留代码前，是否有 characterization test（先钉住现有行为的测试）？ | 遗留区域没有测试，改动前不先钉住现有行为 | 小范围、低风险改动可以直接补针对性测试 |
| 测试套件是否慢到没人愿意跑？ | 全量测试超过 10 分钟；慢测试集中在高风险路径 | 少量关键路径的端到端测试是必要的 |

## 快速判定顺序

1. 先看新增或修改的行为有没有对应测试。
2. 再看断言能不能在实现改坏时失败。
3. 再看测试是否只验证 mock 调用。
4. 再看边界、错误和并发路径。
5. 最后看测试层级和运行成本。

## 取证要求

- 指出具体测试文件、用例名或缺失的用例。
- 说明实现改坏时，哪个断言会失败；说不出来，就不算有效断言。
- 测试无法运行时，静态审查断言，并标注「测试行为未实测」。
