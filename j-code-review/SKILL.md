# 先定标准，再审代码

审查只有一个门槛：这次改动是否让系统的整体代码健康变好。不存在完美代码，只存在更好的代码。改动只要让代码健康明确变好，即使不完美，也倾向批准。唯一例外是紧急情况：改动小，且事关重大发布、线上事故、法律或安全；想要快发、临近下班、软截止日都不算紧急。以紧急为由放行的改动，事后必须补审。任何情况下都不接受明确恶化的改动。下文的 CL 指一次自包含的代码改动。

## 触发边界

满足任一条，用本技能：

- 用户给出 diff、PR、分支、提交范围或文件，并要求审查。
- 用户问「这个 PR 能不能过」「这段改动有没有问题」「cr 一下」。
- 用户要求合并前、发版前或上线前的代码健康审视。

不触发，改用其他方式：

| 用户要做的事 | 用什么 |
| --- | --- |
| 修 bug、重构、生成代码 | 直接实现；本技能只审查，不改代码 |
| 跑测试、看覆盖率 | 测试工具或对应命令 |
| 审查文档、设计稿、文案 | 对应文档审查流程 |
| 多轮「修复—复审」收敛 | review-bounded |
| 只做格式化、lint 修复 | 格式化与 lint 工具 |
| 前端专项检查表评分 | frontend-code-review；可作本技能补充输入，结论仍由本技能给 |
| 专项安全审计 | security-review 或对应安全流程；本技能只把安全问题计入 P0/P1 |
| 代码健康度评分（0–100） | yotta-code-quality；本技能不产出健康分，只给合并结论 |
| 框架或技术栈专项审查 | 对应的专项技能；专项结论作为输入，总体结论仍由本技能给 |

## 输入类型判断

| 输入 | 动作 |
| --- | --- |
| PR 号或链接 | 用 `gh pr diff <n>` 或等价命令取 diff；读变更文件全文与相关测试 |
| 分支或提交范围 | 用 `git diff <base>...<head>` 取 diff；先确认 base 和 head |
| 单个文件或目录 | 读文件、调用方与相关测试；用 `git diff` 确认改动来源；没有 git 历史时，按用户说明的范围审，并声明基线未知 |
| 只有文字描述，没有 diff | STOP：先要 diff、文件或提交范围 |
| 整个仓库体检 | 声明范围；按模块分节审；不下跨文件结论 |

## 审查模式

| 模式 | 触发条件 | 覆盖范围 | 输出 |
| --- | --- | --- | --- |
| 快速扫描 | 用户明确只要速扫、只看风格；或改动小于 50 行、单文件、不涉及高风险区 | P0/P1、明显结构红旗、本次改动直接引入的问题 | 短报告：结论 + 发现 + 验证与范围 |
| 标准审查 | 默认；改动 50–500 行，或规模未知 | 全部维度 + 行为链路 + 结构红旗 | 完整报告 |
| 发布前全量 | 用户说发版前、全量、上线前；或改动大于 500 行且用户拒绝拆分 | 按子系统分节，逐节结论，最后给整体结论；可拆多轮 | 分节报告 + 整体结论 |

高风险区包括认证、权限、支付、数据删除、数据迁移、并发与事务。改动落在高风险区时，至少用标准审查。改动大于 500 行时，先按失败分支表建议拆分；用户拒绝后，再用发布前全量模式。CL 大到无法一次审透（大于约 1000 行，或散布到几十个文件）时，「CL 过大应拆分」本身列为 P2 发现，不只是调整审查方式。发布前全量按子系统派独立审查者并行读全文，主线只保留跨模块状态机、不变量与失败路径的推演；子代理返回后，主线必须复核其关键证据（文件:行号）再采纳。每轮子审查的范围控制在约 15 个文件；给足 8–10 分钟。子代理完成会自动通知。不要轮询相对时间判断进度；不要中途停止；不要发「立即收束」消息，它会多触发一轮并打断节奏。范围过大时先拆轮，不靠催收压缩时间。

## 工作流

1. 确认审查对象与意图。先问改动要实现什么，再问谁是用户：终端用户，以及未来读代码的开发者。意图对用户无益，或加入了系统不想要的特性时，实现再漂亮也拒绝。
2. 取 diff 与基线。确认 base 和 head。把本次改动引入的问题和基线已有的问题分开。文件出现在 diff 中，不等于它是根因。存量缺陷不归因于本次改动，除非本次改动暴露了它。
3. 选择审查模式。按上表判断。用户要求一次审完大改动时，不拒绝，改为按子系统分节输出。
4. 读变更文件全文，不只读 diff。读调用方、被调用方、相关测试、配置和文档。分配给你的每一行都要读懂。你读不懂，别人也读不懂。代码阅读是审查的核心动作。代码阅读擅长发现接口与结构缺陷，与测试互补。单位时间发现的缺陷约为执行测试的两倍。同时跳出 diff，看整个文件和整个系统。改了 4 行，可能意味着那个 50 行的方法该拆了。不接受让小复杂度悄悄累积的改动。
5. 沿输入到输出的链路推演一遍。步骤查 `references/review-checklist.md` 的「行为链路」表。
6. 按维度顺序审查。细项查 `references/review-checklist.md`。语言专项查 `references/language-hotspots.md`，测试腐化查 `references/test-quality.md`。
7. 主动找能删除复杂度的机会。判定信号查 `references/structure-red-flags.md`。
8. 过滤发现名单。报出前，先核对异常处理、默认值、调用方约束和框架行为。风险已被消解的，不进列表。项目文档或审计记录里「已记债 / 本版放行」的技术问题，若技术上仍成立，保留为 P2/P3 并标注「已记债」，不得移出发现列表；记债是排期决定，不是风险消失的证据。记债要有凭据：落了 bug 单和引用该单的 TODO 才算。「以后清理」的口头承诺不构成记债，本次新引入的复杂度必须在本 CL 内清理。
9. 定级。按上线后会发生什么定级，不按修复难度定级。
10. 写评论。每条评论带分级前缀。每条阻止项写全三要素：文件:行号、为什么是恶化、改法方向。
11. 执行最终自检。逐项查「最终自检」清单。
12. 按 `assets/review-report-template.md` 输出，并给明确结论。

## 维度顺序（即优先级）

1. **Design**：最重要，先审。看各部分交互、改动该落在本代码库还是某个库、如何与系统集成、现在是不是恰当时机。再判断模块够不够**深**：接口（使用成本）远小于功能（收益）才是深模块。接口复杂度接近功能的模块是**浅模块**，红旗。再看语义归属：行为的状态、变更权、生命周期、不变量和失败策略有没有唯一所有者；同一事实有没有多个可写来源。
2. **Functionality**：实现是否符合意图。主动推演边界情况、并发问题（死锁与竞态）、用户视角能发现的 bug。按典型错误类别过一遍：结构、数据、实现与意图不符、构造、集成、需求理解、测试定义。改动有用户可见影响且读代码判不了时，声明「需人工演示或试用验证」，列入验证与搜索空间，不假设能验证。
3. **Complexity**：读者是否能快速理解。用三个症状判断：**变更放大**（改一处要动多处）、**认知负担**（读者要多知道多少）、**未知的未知**（看不出要改哪里、哪里会出问题）。只解决现在已知的问题，拒绝为猜测中的未来需求做过度工程。
4. **Errors / Contracts**：先问能不能重定义语义，让错误情形消失，而不是增加处理分支。异常是接口的一部分：异常越多，接口越复杂，模块越浅。再查错误处理代码自身有没有引入新异常。
5. **Tests**：按改动类型要求单元、集成或端到端测试。改了行为却没有对应测试，本身是发现（紧急情况除外）。逐个检查：代码改坏时测试会不会失败？会不会假阳性？断言有没有用？测试也是要被维护的代码。测试腐化按 `references/test-quality.md` 的 T1-T6 查。
6. **Naming**：名字要长到能说清是什么、做什么，但不再更长。作用域越大，名字越长、越精确。按问题域命名，不按实现细节命名。
7. **Comments**：注释解释代码存在的**原因**，不解释代码做什么。代码不清楚时先简化代码，不要靠加注释。清掉已失效的旧 TODO。正则与复杂算法是解释性注释的例外。用了反直觉或不直观的技术时，注释必须写明直白的做法和收益。
8. **Style / Consistency**：以项目 style guide 为最高权威。纯个人偏好不阻塞提交。重大风格改动独立成一个改动，不和功能混在一起。style guide 没规定时，与现有代码保持一致，并留 TODO 清理旧代码。
9. **Documentation**：改动影响构建、测试、交互或发布方式时，同步更新文档。删代码时，考虑同步删掉文档。

## 结构与抽象红旗

在上述维度之外，主动找能**删除复杂度**的机会。不要只把代码收拾得干净一点。复杂度由依赖和模糊累积而成。对小恶化零容忍。

- **浅模块 / 薄 wrapper**：接口复杂度和功能相当。没有收益的 wrapper 只增加间接层。透传方法的红旗：纯转发、签名相同、没有新增功能。
- **信息泄漏**：同一份知识（文件格式、协议结构、魔法字符串前缀）出现在多个模块。按执行顺序拆模块（时间顺序分解）是常见成因。不暴露在接口里的后门泄漏更难发现。
- **面条式特例增长**：把临时条件、特例、一次性 flag 不断拼接到已有路径上。这类逻辑该放进显式的状态模型或专用抽象。
- **重复**：同样的代码反复出现，说明还没找到正确的抽象。合并前先确认两块代码确实共享信息、一起使用、概念重叠；否则分开更好。
- **连体方法**：拆开后必须互相参照才能理解的方法，不该拆。深度优先于长度：几百行但接口简单的方法，可以是好模块。
- **透传变量**：中间参数只为把值从上层传到下层而存在时，改用 context 对象或共享对象。
- **类属炎（classitis）**：为拆而拆出一堆小类和小方法，接口总数爆炸，系统级复杂度反而上升。不要按行数机械拆分。
- 偏好直接、无聊、可维护的代码。「也许改个名」级别的建议不算数。已经有明显更简单的思路时，不接受把同一思路稍作收拾的版本。

详细判定信号和改法见 `references/structure-red-flags.md`。

## 看见好的要指出来

很好的简化、好的测试覆盖、对评论的好回应，都值得指出，并说明为什么好。指出优点和指出问题一样，都能塑造行为。这条不占发现列表的编号，放在报告末尾一句即可。

## 写评论

- **友善、说明理由**：只评论代码，永远不评论开发者。说清为什么这样改能改善代码健康。修正是作者的责任；指出问题的方式，要能帮作者学到东西并拿到更好的方案。教学性观点标 `Nit:` 或 `FYI:`，不把评审变成强制课程。
- **分级，让意图明确**（原文前缀）：
  - `Nit:` 小事，技术上应该做但不影响大局
  - `Optional (or Consider):` 建议，非必须
  - `FYI:` 不指望这个 CL 处理，供以后思考
- **不依赖口头解释**：看不懂的代码，要求作者重写得更清楚，或者在代码里加注释。解释只写在评审工具里，对未来读者没有帮助。
- **冲突处理**：技术和数据优先于个人偏好。风格以 style guide 为权威。设计问题按底层原则权衡；作者能用数据或坚实的工程原则证明多方案等效时，接受作者的偏好。僵持不下就面对面讨论，并把结论记录回评论。还不行就升级给技术负责人。别让 CL 因僵局搁置。

## 失败分支与检查点

审查偏离正向流程时，按下表处理，不静默跳过：

| 触发条件 | 一线修复 | 仍失败的兜底 |
| --- | --- | --- |
| 意图不明或无 diff | 🔴 **STOP**：先问清审什么、范围多大，不澄清不开审 | 用户只给「全量体检」授权时：开头声明范围，逐文件审，不下跨文件的结论 |
| 修复后复审 / 多轮复审 | 重读工作区的最新代码（diff + 文件），不许凭会话记忆推断代码状态 | 同一问题换个措辞再出现，不算新发现（跨轮去重）；修复引入的新代码本身也是审查对象 |
| 改动大于约 500 行，或文件大于 1000 行 | 🔴 **STOP**：建议按模块拆成多轮审查，先审核心路径 | 用户要求一次审完时：按子系统分节输出，每节独立结论，最后给整体判断 |
| 子审查者长时间未返回 | 先确认单轮范围是否超过约 15 个文件；范围过大就拆小重派，并按 8–10 分钟等待 | 完成会自动通知：不要轮询相对时间、不要中途停止或发催收消息；确属卡死再停止并缩小范围重派 |
| 某段代码读不懂 | 按「我读不懂 = 别人也读不懂」，推动重写或加注释 | 仍不清楚：请作者讲解，把结论写成代码注释后再评；仅凭口头解释不批准 |
| 测试无法运行或不存在 | 静态审查测试代码本身：断言在实现改坏时会不会真的失败 | 输出中标注「测试行为未实测」，不把「看起来有测试」当通过依据 |
| 只有部分文件可审 | 开头声明审查范围 | 只给范围内的结论，明确说「未审 X」 |
| 生成代码 / vendored 代码混入 diff | 跳过不审，开头注明 | 生成代码的缺陷反馈给生成器配置，不逐行评论 |
| 与作者僵持不下 | 面对面讨论，把结论记录回评论 | 升级给技术负责人裁决；🛑 不让 CL 因僵局搁置，也不因僵持而放行 |

## 输出格式

先定严重度，再写评论。每条发现按「**上线后会发生什么**」定级，不按修复难度定级：

| 级别 | 定义 | 结论映射 |
| --- | --- | --- |
| **P0** | 直接导致崩溃、死锁、数据丢失或损坏、安全漏洞、核心功能不可用 | 阻止项 |
| **P1** | 确定是 bug，但有绕行办法或影响范围有限；或明确违反验收标准 | 阻止项 |
| **P2** | 行为正确，但存在真实的健壮性、性能、一致性或可维护性风险 | 需修改后批准，或带强烈建议批准 |
| **P3** | 非功能性建议：风格、命名、注释、结构调整 | `Nit:` / `Optional:` |

没有具体失败场景的观察，不上 P0/P1。纯个人偏好不记录。测试断言必须在目标行为回归时真实失败；做不到这一点，断言本身就是缺陷，不能当证据。

评论按严重度分组：P0 → P1 → P2 → P3。同一级别内，按结构性回退 → 错过简化机会 → 复杂度 / 面条式增长 → 边界与契约问题 → 文件大小与拆分 → 可读性排序。每条评论都带分级前缀和严重度。每条阻止项必须三要素齐全：

1. **文件:行号**
2. **为什么是恶化**（违反了哪条维度）
3. **改法方向**（改成什么样，不写「建议优化」）

「为什么是恶化」要写清症状、触发条件、上线后果。只写症状和改法、不写后果的评论，算噪音。

🛑 **CHECKPOINT · 下任何结论前必须自查**（批准和拒绝都要查）：

1. **先陈述反对理由**：批准前，列出最强的「不应合并」理由（最多 3 条）；拒绝前，列出最强的「可以接受」理由。每条理由标注证据强度：
   - `代码证据`：diff 中直接可见
   - `测试证据`：有测试输出
   - `推测`：无直接证据

   批准结论里存在带 `代码证据` 的 P0/P1 时，禁止批准。
2. **过滤发现名单**：每条候选在报出之前，先核对异常处理、默认值、调用方约束和框架行为，看它们是否已经消除了该风险。能消解的不进列表。
   每处阻止项必须有具体代码证据（文件:行号 + 为什么是恶化），并且不存在可以接受的更小改法。不为了凑数而写拒绝理由。
   只能证明到「值得确认」的问题，单独列入「待确认事项」：不混进发现列表，也不降级成 `Optional:`。「待确认」指缺上下文判不了；`Optional:` 指建议改但不强制。
3. **声明验证与搜索空间**：如实列出实际跑过的命令和结果，用四种状态标注：已运行并通过 / 未实测 / 运行失败 / 无法验证。再列出本次没有覆盖的维度和文件（例如「并发路径未审」「只审了 src/」）。无论结论如何都要声明，零发现时也要声明：「没发现问题」只意味着「在已搜范围内没发现」。

结论只能从以下三个中选一个：**批准（含附带评论）/ 需修改后批准 / 拒绝**，并说明依据哪条标准。证据不足，或疑虑无法消除时，不下批准结论。

报告必须包含：结论、审查对象与范围、变更判定、发现列表、待确认事项、反对理由与证据强度、已核对但不列出、验证与搜索空间、下一步。完整字段和顺序见 `assets/review-report-template.md`；快速扫描模式用同一模板的简版。

输出禁止项：

- 不写没有位置的问题。
- 不写「建议优化」这类没有方向的建议。
- 不把待确认事项混进发现列表。
- 不把口头解释当澄清。
- 不在没跑过测试时写「测试已验证」。
- 不用 `Nit:` 淹没结构问题。

## 最终自检

输出前逐项检查：

1. 结论是否只有一个，且属于三个选项之一？
2. 每条 P0/P1 是否都有文件:行号、为什么是恶化、改法方向、证据强度？
3. 批准结论前，是否列出了最强的反对理由？存在带代码证据的 P0/P1 时，是否没有批准？
4. 是否把本次引入的问题和基线已有问题分开？
5. 是否过滤了已被异常处理、默认值、调用方约束或框架行为消解的候选？
6. 是否把只能证明到「值得确认」的问题放进了待确认事项，而不是发现列表？
7. 验证状态是否如实标注？没跑过的测试是否写了未实测？
8. 是否声明了未覆盖的维度和文件？
9. 快速扫描模式是否只输出结论、审查对象与范围、发现、验证与范围？
10. 是否避免了只写在评审工具里的口头解释？

## 交付与复用

产出是一份可直接粘贴到 PR/MR 的审查报告。用户要求落盘时，保存为 `review-report.md`。报告里的每条评论都能直接使用：位置、原因、改法方向齐全。

按结论分流下一步：

- **批准**：合并。
- **需修改后批准**：作者按发现清单修改，改完复审。
- **拒绝**：作者重新设计或拆分改动。

需要多轮收敛审查（修一轮、审一轮，要收敛判定）时，把发现清单交给 review-bounded 技能。本技能只做单次审查。
