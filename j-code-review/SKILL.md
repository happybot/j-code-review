# 先定标准，再审代码

审查只有一个门槛：**这次改动是否让系统的整体代码健康变得更好**。不存在完美代码，只存在更好的代码。只要 CL 明确改善了代码健康，即使不完美，也应倾向批准。唯一例外是紧急情况；任何情况下都不接受明确恶化的改动。标准出处：Google Engineering Practices 审查三篇、A Philosophy of Software Design 2e（下称 APoSD）、Code Complete、借用自 thermo-nuclear 系列的激进简化维度。

## 判断步骤

1. **确认审查对象与意图**：先问改动要实现什么，再问谁是"用户"（终端用户 + 未来读代码的开发者）。意图对用户无益时，实现再漂亮也拒绝。
   把本次改动引入的问题和基线已有的问题分开。文件出现在 diff 中，不等于它是根因。存量缺陷不归因于本次改动，除非本次改动暴露了它。
2. **逐维度检查**（顺序即优先级）：
   - **Design**：最重要，先审这层。检查各部分交互是否合理、改动该落在本代码库还是某个库、怎么与系统集成、现在是不是加这个功能的恰当时机。
     再看新模块够不够**深**：深指接口（使用成本）远小于功能（收益）。接口复杂度接近功能的模块是**浅模块**，红旗（APoSD Ch4）。
   - **Functionality**：检查实现是否符合意图。主动推演边界情况、并发问题（死锁与竞态）、用户视角能发现的 bug。
     沿输入到输出追踪一遍：
     - 入口与调用方；
     - 参数、状态、异常与返回值的流向；
     - 数据格式、权限、生命周期、事务与并发边界；
     - 相关测试和配置里的既有约定。
     再按典型错误类别过一遍：结构 / 数据 / 实现与意图不符 / 构造 / 集成 / 需求理解 / 测试定义（Code Complete）。
     改动有用户可见影响时，可以要求演示。
   - **Complexity**：检查每一层是不是让读者无法快速理解。用三个症状判断（APoSD Ch2）：
     - **变更放大**：改一处要动多处；
     - **认知负担**：读者要多知道多少才能用；
     - **未知的未知**：看不出要改哪里，也看不出哪里会出问题。
     只解决现在已知的问题，拒绝为猜测中的未来需求做过度工程。
   - **Errors / Contracts**：先问能不能重定义语义，让"错误情形"消失，而不是增加处理分支。异常是接口的一部分：异常越多，接口越复杂，模块越浅。再检查错误处理代码自身有没有引入新异常（APoSD Ch10）。
   - **Tests**：按改动类型要求单元、集成或端到端测试。逐个检查：代码改坏时测试会不会失败？会不会假阳性？断言有没有用？测试也是要被维护的代码。
   - **Naming**：名字要长到能说清"是什么/做什么"，但不再更长。作用域越大，名字应越长、越精确。按问题域命名，不按实现细节命名（Code Complete）。
   - **Comments**：注释解释代码存在的**原因**，不解释代码做什么。代码不清楚时先简化代码，不要靠加注释。清掉已失效的旧 TODO。正则与复杂算法是解释性注释的例外。用了反直觉或不直观的技术时，注释必须写明直白的做法是什么、这么做的收益有多少（Code Complete: document surprises）。
   - **Style / Consistency**：以项目 style guide 为最高权威。纯个人偏好不阻塞提交。重大风格改动独立成一个改动，不和功能混在一起。style guide 没规定时，与现有代码保持一致，并留 TODO 清理旧代码。
   - **Documentation**：改动影响构建、测试、交互或发布方式时，同步更新文档。删代码时，考虑同步删掉文档。
3. **看每一行，也看上下文**：分配给你的每一行都要读，并且读懂——你读不懂，别人也读不懂。
   代码阅读是审查的核心动作：它擅长发现接口与结构缺陷，与测试互补，单位时间发现的缺陷远多于执行测试（Code Complete）。
   同时跳出 diff，看整个文件和整个系统：改了 4 行，可能意味着那个 50 行的方法该拆了。
   不接受让小复杂度悄悄累积的改动。
4. **看到好的要指出来**：很好的简化、好的测试覆盖、对评论的好回应，都值得指出，并说明为什么好。指出优点和指出问题一样，都能塑造行为。

## 结构与抽象红旗

在 Google 各维度之外，主动找能**删除复杂度**的机会，不要只把代码收拾得"干净一点"。复杂度由依赖和模糊累积而成。对小恶化零容忍（APoSD Ch2）：

- **浅模块 / 薄 wrapper**：接口复杂度和功能相当的模块，对抗不了复杂度。没有收益的 wrapper 只增加间接层，不做任何简化（APoSD Ch4/Ch7）。透传方法的红旗：纯转发、签名相同、没有新增功能。
- **信息泄漏**：同一份知识（文件格式、协议结构、魔法字符串前缀）出现在多个模块，就是红旗。不暴露在接口里的"后门泄漏"更难发现。常见成因是按执行顺序拆模块（时间顺序分解）（APoSD Ch5）。
- **面条式特例增长**：把临时条件、特例、一次性 flag 不断拼接到已有路径上，是设计问题。这类逻辑该放进显式的状态模型或专用抽象。
- **重复**：同样的代码反复出现，说明还没找到正确的抽象。但合并前先确认两块代码确实共享信息、一起使用、概念重叠；否则分开更好（APoSD Ch9 重复红旗与合并信号）。
- **连体方法**：拆开后必须互相参照才能理解的方法，不该拆。深度优先于长度：几百行但接口简单的方法，可以是好模块（APoSD Ch9.7）。
- **透传变量**：中间参数只为把值从上层传到下层而存在时，考虑改用 context 对象或共享对象（APoSD Ch7.5）。
- **类属炎**：为拆而拆出一堆小类和小方法，接口总数爆炸，系统级复杂度反而上升。不要按行数机械拆分（APoSD Ch4.6/Ch9.8）。
- 文件越过 1000 行红线时优先拆分，除非有强的结构理由（thermo 借鉴）。
- 偏好直接、无聊、可维护的代码。"也许改个名"级别的建议不算数；已经有明显更简单的思路时，不接受把同一思路稍作收拾的版本（thermo 借鉴）。

## 写评论

- **友善、说明理由**：只评论代码，永远不评论开发者。说清为什么这样改能改善代码健康。修正是作者的责任；但指出问题的方式，要能帮作者学到东西并拿到更好的方案。
- **分级，让意图明确**（原文前缀）：
  - `Nit:` 小事，技术上应该做但不影响大局
  - `Optional (or Consider):` 建议，非必须
  - `FYI:` 不指望这个 CL 处理，供以后思考
- **不依赖口头解释**：看不懂的代码，要求作者重写得更清楚，或者在代码里加注释。解释只写在评审工具里，对未来读者没有帮助。
- **冲突处理**：技术和数据优先于个人偏好。风格以 style guide 为权威。设计问题按底层原则权衡；作者能用数据或坚实的工程原则证明多方案等效时，接受作者的偏好。僵持不下就面对面讨论，并把结论记录回评论。还不行就升级给技术负责人。别让 CL 因僵局搁置。

## 失败分支与检查点

审查偏离正向流程时，按下表处理，不静默跳过：

| 触发条件 | 一线修复 | 仍失败的兜底 |
| --- | --- | --- |
| 意图不明或无 diff | 🔴 **STOP**：先问清审什么、范围多大，不澄清不开审 | 用户只给"全量体检"授权时：开头声明范围，逐文件审，不下跨文件的结论 |
| 修复后复审 / 多轮复审 | 重读工作区的最新代码（diff + 文件），不许凭会话记忆推断代码状态 | 同一问题换个措辞再出现，不算新发现（跨轮去重）；修复引入的新代码本身也是审查对象 |
| 改动大于约 500 行，或文件大于 1000 行 | 🔴 **STOP**：建议按模块拆成多轮审查，先审核心路径 | 用户要求一次审完时：按子系统分节输出，每节独立结论，最后给整体判断 |
| 某段代码读不懂 | 按"我读不懂 = 别人也读不懂"，推动重写或加注释 | 仍不清楚：请作者讲解，把结论写成代码注释后再评；仅凭口头解释不批准 |
| 测试无法运行或不存在 | 静态审查测试代码本身：断言在实现改坏时会不会真的失败 | 输出中标注"测试行为未实测"，不把"看起来有测试"当通过依据 |
| 只有部分文件可审 | 开头声明审查范围 | 只给范围内的结论，明确说"未审 X" |
| 生成代码 / vendored 代码混入 diff | 跳过不审，开头注明 | 生成代码的缺陷反馈给生成器配置，不逐行评论 |
| 与作者僵持不下 | 面对面讨论，把结论记录回评论 | 升级给技术负责人裁决；🛑 不让 CL 因僵局搁置，也不因僵持而放行 |

## 输出

先定严重度，再写评论。每条发现按"**上线后会发生什么**"定级，不按修复难度定级：

- **P0**：直接导致崩溃、死锁、数据丢失/损坏、安全漏洞或核心功能不可用
- **P1**：确定是 bug，但有绕行办法或影响范围有限；或明确违反验收标准
- **P2**：行为正确，但存在真实的健壮性、性能、一致性或可维护性风险
- **P3**：非功能性建议：风格、命名、注释、结构调整

定级与结论的映射：

- P0/P1 → 阻止项（拒绝，或需修改后批准）
- P2 → 需修改后批准，或带强烈建议批准
- P3 → `Nit:` / `Optional:`

没有具体失败场景的观察，不上 P0/P1。纯个人偏好不记录。测试断言必须在目标行为回归时真实失败；做不到这一点，断言本身就是缺陷，不能当证据。

评论按这个顺序组织：结构性回退 → 错过简化机会 → 复杂度/面条式增长 → 边界与契约问题 → 文件大小与拆分 → 可读性。每条评论都带分级前缀和严重度。每条阻止项必须三要素齐全：

1. **文件:行号**
2. **为什么是恶化**（违反了哪条维度）
3. **改法方向**（改成什么样，不写"建议优化"）

🛑 **CHECKPOINT · 下任何结论前必须自查**（批准和拒绝都要查）：

1. **先陈述反对理由**：批准前，列出最强的"不应合并"理由（最多 3 条）；拒绝前，列出最强的"可以接受"理由。每条理由标注证据强度：
   - `代码证据`：diff 中直接可见
   - `测试证据`：有测试输出
   - `推测`：无直接证据

   批准结论里存在带 `代码证据` 的 P0/P1 时，禁止批准。
2. **过滤发现名单**：每条候选在报出之前，先核对异常处理、默认值、调用方约束和框架行为，看它们是否已经消除了该风险。能消解的不进列表。
   每处阻止项必须有具体代码证据（文件:行号 + 为什么是恶化），并且不存在可以接受的更小改法。不为了凑数而写拒绝理由。
   只能证明到"值得确认"的问题，单独列入"待确认事项"：不混进发现列表，也不降级成 `Optional:`。"待确认"指缺上下文判不了；`Optional:` 指建议改但不强制。
3. **声明验证与搜索空间**：如实列出实际跑过的命令和结果，用四种状态标注：已运行并通过 / 未实测 / 运行失败 / 无法验证。再列出本次没有覆盖的维度和文件（例如"并发路径未审""只审了 src/"）。无论结论如何都要声明，零发现时也要声明："没发现问题"只意味着"在已搜范围内没发现"。

最后给出明确结论：批准（含附带评论）/ 需修改后批准 / 拒绝，并说明依据哪条标准。证据不足，或疑虑无法消除时，不下批准结论。

需要多轮收敛审查（修一轮、审一轮，要收敛判定）时，改用 review-bounded 技能。本技能只做单次审查。

## 审查黑名单（不要做什么）

- 不评论开发者本人，只评论代码。
- 不因纯个人风格偏好阻塞提交；不把教学性观点当强制要求。
- 不用 Nit 淹没更大的结构问题。有结构问题时，优先给少而高确信的评论。
- 不接受只写在评审工具里的口头解释当澄清。结论必须落回代码或注释。
- 不放行明确恶化的改动（死代码、面条式特例、薄 wrapper、越线文件膨胀）。唯一的"紧急"例外必须真实，且事后补审。
- 不替作者做详细设计，也不代写大段实现。指出问题、给出方向，修正是作者的责任。
- 不声称"测试已验证"。没跑过就标"未实测"。

## 不适用情形

- 没有改动意图或 diff 时，先问清审什么，不凭空审整个仓库。
- 作者明确只要语法/风格速扫时，只做该范围，并在开头注明。
- 借来的激进简化维度不凌驾于项目授权。作者能用工程原则证明方案等效时，接受作者的选择。
- 教学性评论标 `Nit:` 或 `FYI:`，不把评审变成强制课程。
