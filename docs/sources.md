# 标准来源

本文是 [README](../README.md) 的补充材料，记录 j-code-review 的规则各自从哪来。

规则不是自拟的，拼装自六份来源。前三份是公开规范与著作；后三份是技能，权威性低于前三份，也不凌驾于项目授权。SKILL.md 里每条规则都带行内引用，例如 `APoSD Ch5`、`Code Complete`。据此可以逐条回溯到本文件。

## Google Engineering Practices

Google 公开的代码审查规范，分「代码审查者指南」与「变更作者指南」两组。它是整套标准里最主要的一份。CL（changelist，一次自包含的变更）等术语也出自这份文档。

出处：https://google.github.io/eng-practices/

本技能借用：

- 整体代码健康这个唯一门槛
- `Nit:` / `Optional (or Consider):` / `FYI:` 三个评论前缀
- 只评论代码，不评论开发者
- 冲突时技术与数据优先于个人偏好
- 僵持时面对面讨论，并把结论记录回评论
- 仍不能解决则升级给技术负责人，不让 CL 因僵局搁置

## A Philosophy of Software Design, 2e（John Ousterhout）

技能里标注 APoSD 的引用，都出自这本书。下面列出借用的章节和对应规则：

- Ch2 复杂度的本质：三个症状是变更放大、认知负担、未知的未知。复杂度由依赖和模糊累积，所以对小恶化零容忍
- Ch4 深模块：接口成本远小于功能收益的模块，才对抗得了复杂度。接口复杂度接近功能，就是浅模块。Ch4.6 讲类属炎
- Ch5 信息隐藏：同一份知识散落多处，就是信息泄漏。这类知识包括文件格式、协议结构、魔法字符串前缀。常见成因是按执行顺序拆模块，也就是时间顺序分解。这样拆会诱发后门泄漏，即不暴露在接口里的泄漏
- Ch7 不同层不同抽象：纯转发的透传方法，特征是签名相同、没有新增功能。透传变量只为把值从上层传到下层而存在（Ch7.5）
- Ch9 合还是分：连体方法不该拆。看到重复时先确认两块代码共享信息、一起使用、概念重叠，再决定合并。Ch9.7 讲深度优先于长度，Ch9.8 讲不按行数机械拆分
- Ch10 让错误情形消失：优先重定义语义，不要给错误处理加分支。异常是接口的一部分，异常越多，接口越复杂

## Code Complete, 2e（Steve McConnell）

- 命名按问题域，不按实现细节。名字长度随作用域增长
- 注释解释代码存在的原因，不解释代码的做法。用了反直觉的技术时，要写明直白的做法和这么做的收益（document surprises）
- 典型错误类别清单：结构 / 数据 / 实现与意图不符 / 构造 / 集成 / 需求理解 / 测试定义
- 单位时间里，读代码发现的缺陷远多于执行测试。这条是审查以读代码为核心、测试只作补充的依据

## review-bounded（外部技能，MIT）

网友 ZM-BAD 写的三轮有界代码审查技能：https://github.com/ZM-BAD/review-bounded

review-bounded 解决的是 AI 审查没有终止条件的问题。它固定跑三轮「审查—修复」循环，每轮修复前要用户授权，最后给出收敛判定。j-code-review 只审一次，两者定位互补：本技能管判断标准，review-bounded 管执行纪律。融合发生在 2026-10-14 的第一轮优化。

本技能只借它的纪律，不借它的编排：

- P0–P3 严重度标尺的四条定义（对应它的 `references/rubric.md`）
- 按「上线后会发生什么」定级，不按修复难度定级
- 没有具体失败场景的观察不上 P0/P1，纯个人偏好不记录
- 断言必须能在目标行为回归时真实失败。做不到这一点，断言本身就是缺陷，不能当证据
- 下结论前先说出最强的反对理由，批准和拒绝都要说（对应它的 the case against merging）。每条理由标注证据强度：`代码证据` / `测试证据` / `推测`
- 存在带 `代码证据` 的 P0/P1 时，禁止批准（对应它的 the verdict MUST be NOT CONVERGED）
- 复审时重读工作区的最新代码，不凭会话记忆推断。同一个问题换个措辞再出现，不算新发现（跨轮去重）
- 验证状态如实标注：没跑过就写未实测，不把代码阅读结果写成测试通过

明确没借的有三项：三轮循环、收敛判定模板、授权—修复流程。这三项属于编排层，和单次审查的定位冲突。SKILL.md 末尾只留一句指针，把需要多轮收敛的场景交给 review-bounded。

## precision-code-review（外部技能）

网友 ydpzg 写的证据优先代码审查技能：https://github.com/ydpzg/precision-code-review

融合发生在 2026-10-14 的第二轮优化，当时用的是其中的 SKILL.md 单文件。下面这些借用条目，已和远端 SKILL.md 核对一致。

本技能借用：

- 沿输入到输出追一遍行为链路。顺序是：入口与调用方 → 参数、状态、异常与返回值的流向 → 数据格式、权限、生命周期、事务与并发边界 → 相关测试和配置里的既有约定
- 把本次变更引入的问题和基线已有的问题分开。文件出现在 diff 中，不等于它是根因。存量缺陷不归因于本次变更，除非本次变更暴露了它
- 过滤发现名单。上报每条候选前，先核对异常处理、默认值、调用方约束和框架行为，确认这些有没有消除风险。能消除的不进列表
- 只能证明到「值得确认」的问题，单独列入待确认事项。这类问题不混进发现列表，也不降级成 `Optional:`
- 验证状态分四种如实标注：已运行并通过 / 未实测 / 运行失败 / 无法验证

## thermo-nuclear 系列（外部技能）

社区流传的严格审查技能系列，例如 thermo-nuclear-code-quality-review。它取自 Cursor 的 plugins 仓库，立场是激进简化。这部分是借来的实践规则，所以在 SKILL.md 里单独成节，也不凌驾于项目授权。

被借用：

- 文件 1000 行红线
- 把临时条件、特例、一次性 flag 的堆积（面条式增长）当设计问题
- 优先删除复杂度，不要只把同一思路收拾干净
- 拒绝「也许改个名」级别的建议
- 偏好直接、无聊、可维护的代码
